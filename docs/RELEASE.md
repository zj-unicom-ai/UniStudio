# UniStudio 发版规范

本文约定仓库本身的版本号和正式发版流程。视频模板中的 HyperFrames 依赖版本、单期视频版本和制作任务状态各自独立，不作为 UniStudio 仓库版本。

## 版本号

采用语义化版本号，格式为 `vMAJOR.MINOR.PATCH`，例如 `v0.2.1`。Git 中带 `v` 的正式标签是版本号的唯一来源；每个正式版本必须有且只有一个对应标签，并在根目录 `CHANGELOG.md` 留下记录。

- **MAJOR（主版本）**：有不兼容变更，例如 CLI 参数或配置格式破坏兼容、任务数据需要不兼容迁移，或主要工作流程发生不兼容调整。
- **MINOR（次版本）**：增加向后兼容的用户能力，例如新模板、发布平台、看板功能或 CLI 能力。
- **PATCH（修订号）**：向后兼容的问题修复、文档修正、依赖或内部实现更新。

主版本号为 `0` 时仍按上述规则递增；此阶段接口尚未承诺稳定。第一个正式版本从 `v0.1.0` 开始，之后依照变更类型递增。候选版本使用 `vMAJOR.MINOR.PATCH-rc.N`，例如 `v0.2.0-rc.1`；候选版本不替代正式版本标签。

## 变更日志

所有对使用者可见的变更先记到 `CHANGELOG.md` 的「未发布」部分。正式发版时，将本次包含的条目整理到新版本标题下，并写入发版日期（`YYYY-MM-DD`）；未包含的条目继续留在「未发布」部分。记录功能、新增支持、修复、兼容性变化和必要的迁移说明，不记录凭据、本机配置、制作产物或其他运行数据。

## 发版步骤

1. 确认工作区中的改动和发布范围，保留与本次发版无关的用户改动。
2. 按变更类型选择下一个版本号；确认它大于最新正式 `v*` 标签，且未被已有标签使用。没有正式标签时，首次正式版本使用 `v0.1.0`。
3. 整理 `CHANGELOG.md`，为该版本写入日期和面向使用者的变更摘要。
4. 按项目说明验证核心流程：`python3 -m unittest discover -s tests -v`。若本次没有影响可运行行为，可在发版说明中注明未运行及原因。
5. 提交包含变更和变更日志的发版提交，然后在该提交上创建带注释的标签：

   ```sh
   git tag -a v0.1.0 -m "Release v0.1.0"
   ```

   示例中的版本号应替换为实际版本。发版提交和标签需推送到项目远端；若通过 GitHub Releases 分发，则从同名标签创建 Release，并使用对应的变更日志条目作为说明。
6. 核对标签指向发版提交、远端标签可见、`CHANGELOG.md` 有对应版本条目。完成这些检查后，该标签代表正式发版。

任何发版后的修订都创建一个新的递增版本和新标签，不移动或复用已发布标签。仅在本地开发或尚未对外发版的修改不创建正式版本标签。
